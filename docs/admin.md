# Browser administration

The application uses server-rendered HTML and progressive enhancement. Public pages include `/`, `/server/about`, `/server/help`, `/server/privacy`, `/server/terms`, `/server/healthz`, `/robots.txt`, `/sitemap.xml`, and `/manifest.webmanifest`. Static assets use `/static/`, locale catalogs use `/locales/{lang}.json`, and the offline fallback is `/offline.html`. The configurable `/server/{admin_path}` prefix hosts the Server Admin panel.

When `server.users.enabled` is true and `server.users.registration.mode` is `open`, `/server/auth/register` provides a server-rendered regular-user registration form. It checks configured email-domain restrictions and applies the registration rate limit. If email verification is required and SMTP delivery succeeds, the new account stays disabled until the one-time link at `/server/auth/verify/{token}` is used; the welcome email is sent after verification. If email delivery is unavailable, the account is activated without verification as specified by the registration configuration, and the welcome email is attempted only when SMTP is enabled.

## Server Admin pages

The Server Admin log viewer is `/server/{admin_path}/logs`. It filters the current access, error, audit, security, server, or debug log by text, displays at most 500 recent matching entries, provides previous/next navigation, and downloads the current filtered page as JSON or CSV. Sensitive assignments are masked before display. Non-audit logs can be cleared after CSRF validation and typed confirmation; audit logs are append-only and cannot be cleared. The read-only API endpoint is `/api/{api_version}/server/{admin_path}/logs` and accepts `log`, `limit`, `offset`, and `search` query parameters.

HTTP access logs record response status and byte count. One-time tokens and credential-like query parameters are redacted from request paths and referrers before the log entry is written.

The Server Admin mail queue page is `/server/{admin_path}/mail/queue`. It shows Postfix queue metadata without message contents and supports flush, hold, release, retry, and delete actions. Each form action requires CSRF validation and an explicit `yes` confirmation; actions are recorded in the audit log.

The Server Admin information page is `/server/{admin_path}/info`. It reports the build version, commit and date, Go runtime, OS/architecture, database driver availability, configured FQDN, and admin path without exposing secrets.

The Server Admin statistics page is `/server/{admin_path}/stats`. It reports persisted aggregate HTTP request totals, the rolling 24-hour request count, and current in-flight requests.

The Server Admin help editor is `/server/{admin_path}/pages/help`; it saves Markdown to `yaml.d/pages.yml`. The public `/server/help` page renders this content through the shared sanitizer, and `/api/{api_version}/server/help` returns its Markdown source with the help page index. The Server Admin API supports GET and PATCH at `/api/{api_version}/server/{admin_path}/pages/help`.

The Server Admin maintenance page is `/server/{admin_path}/maintenance`. It reports database health, detected database connection failures, and retry status. If the database is unavailable, the page remains available as a read-only diagnostic view without a session so operators can reach recovery guidance. Database failures return canonical 503 maintenance responses for write requests; a background monitor retries connectivity using `server.maintenance.self_healing.retry_interval` (30 seconds by default) and clears the detected failure after recovery unless the configured retry limit is exhausted. On exhaustion, health and audit state report that self-healing stopped, one operator email is attempted when SMTP is ready, and the service remains in maintenance mode until an operator removes the cause and restarts it. Database reconnection, file and disk remediation, cleanup policy, entry/exit notifications, and full diagnostic actions remain open implementation work.

The Server Admin mail delivery log page is `/server/{admin_path}/mail/logs`. It supports bounded search and pagination over delivery envelope metadata, never message contents.

The Server Admin mail statistics page is `/server/{admin_path}/mail/stats`. It defaults to the last 24 hours and supports `24h`, `7d`, or `30d`. It shows sent, received, bounced, deferred, spam, and virus counts, total message bytes from hourly statistics, and the current Postfix queue size. Delivery totals come from stored hourly statistics; queue size is read live from Postfix.

The branding editor is `/server/{admin_path}/branding`. It stores branding, SEO, and UI theme settings in `yaml.d/branding.yml`; HTTPS URLs, data URIs, and uploaded images are accepted. Uploads are limited to 2 MiB per image and stored as mode `0600` files under the private `assets/` directory. The editor also provides OpenGraph and Twitter metadata, canonical origin, extra meta tags, and a site-wide noindex setting.

The email settings page is `/server/{admin_path}/email`. SMTP connection settings are saved in `yaml.d/notifications.yml`; the password is saved in `secrets.yml` and is never returned by the API. A server FQDN is required. On startup, the server probes configured SMTP with EHLO or searches local candidates on ports 25, 465, and 587. Email notifications stay disabled until both the FQDN and SMTP probe are valid. The page reports readiness and can send a test email to a specified recipient using the configured TLS mode. The page and API expose all 16 server-wide event preferences listed in AI.md. Per-admin event overrides are saved on each admin's notifications page and apply to notification emails. Current dispatchers send backup success/failure, SSL renewal failure, generic scheduled-task failure, startup, shutdown, first-login-from-a-new-IP/device, password-change, token-regeneration, and two-factor enable/disable messages; update, disk, database, and remaining account email dispatchers still need implementation.

Email templates are managed at `/server/{admin_path}/email/templates`. Defaults are available immediately; custom subjects and plain text bodies are saved under `template/email/` in the configuration directory. The editor validates supported `{variable}` placeholders, and reset removes the custom version. The versioned API supports listing, reading, updating, previewing, and resetting templates.

The Server Admin mail services page is `/server/{admin_path}/mail/services`. It lists detected service state, enabled state, version, and uptime; operations require a `yes` confirmation, operating-system privileges, and are written to the audit log.

The panel dashboard is `/server/{admin_path}`; `/settings`, `/branding`, `/email`, `/maintenance`, `/info`, `/users`, `/orgs`, `/domains`, `/mail/domains`, `/mail/domains/aliases`, `/mail/transports`, `/mail/queue`, `/scheduler`, `/pages/help`, `/security`, `/security/auth`, `/security/tokens`, `/security/reports`, `/security/policy`, `/security/thanks`, and `/security/keypair` are the current management pages. `/scheduler` reports registered task state and supports CSRF-protected schedule and enabled-state updates plus immediate runs. `/security/auth` provides the Server Admin TOTP enrollment and recovery-code flow. `/security/tokens` shows the active token prefix, rotates the token with a one-time display, and revokes the current token; token hashes are never displayed. `/security/reports` lists and updates disclosure reports; `/security/policy` edits the public Markdown policy; `/security/thanks` manages acknowledgment visibility, credit labels, and display order. `/security/keypair` generates, rotates, imports, deletes, republishes, and exports the project OpenPGP keypair. Sensitive keypair actions require password confirmation; private-key downloads require a reason and are limited to one per admin per hour. `/domains` is reserved for Org and user custom panel domains; `/mail/domains` manages virtual mail domains; `/mail/transports` manages outbound routing rules and reports whether a credential is saved without displaying its value. Mail-domain forms support create, update, and delete by domain ID. Their DKIM card opens `/mail/domains/{id}/dkim`, where Server Admins can create a 2048-bit signing key and view its public DNS value; the private key is encrypted at rest and never displayed. Deletion requires explicit confirmation and is rejected while mailboxes, aliases, DKIM, SPF, DMARC, or transport records depend on the domain. The settings page saves validated application name, FQDN, listen address, one port or an HTTP,HTTPS pair, runtime mode, timezone, daemonize, and PID file values to the active YAML file. Listener, runtime-mode, daemonize, and PID file changes are flagged as requiring a process restart. Account self-service lives under `/server/{admin_path}/{admin_username}/profile`, `/preferences`, `/notifications`, and `/profile/security`. The root `/healthz` alias is disabled by default and is mounted only when `server.healthz.root.enabled` is true.

## First-run setup

Open `/server/{admin_path}/setup` and provide the one-time setup token printed on first start. The wizard collects the initial Server Admin credentials and server settings, validates the token through the versioned verifier endpoint, and displays the generated API token once after completion. Store the API token securely before leaving the completion page.

TOTP is not enabled unless the complete enrollment and recovery-code flow can be completed. Do not enable it from a checkbox alone.

Password recovery is available at `/server/auth/password/forgot` when outbound email is ready. Requests use a generic response whether or not an account exists. Reset links are one-time, SHA-256 hashed at rest, expire after `server.auth.password_reset_ttl` (one hour by default), and invalidate the account's existing sessions when consumed. The API uses `POST /api/{api_version}/server/auth/password/forgot` with `identifier` and `POST /api/{api_version}/server/auth/password/reset` with `token` and `new_password`. The login page also links to `/server/auth/username/forgot` when SMTP is enabled; matching enabled admins and enabled, verified users receive one message containing their username or usernames, with the same generic response for unknown addresses.

## Accounts and organizations

Server Admins and regular mailbox users are separate account families. Mailbox users access `/users`; organizations and their resources are under `/orgs`. Mail-domain management is under `/orgs/{slug}/mail/domains`; custom panel-domain management is under `/orgs/{slug}/domains`. User-owned custom panel domains are managed under `/users/domains`. Mutations use CSRF-protected POST forms. The server passes the authenticated principal and organization scope to its store boundary so persistence can enforce tenant ownership.

Organizations can manage their mailboxes, mail domains, aliases, and members under `/orgs/{slug}/`. Organization mail-domain forms support create, update, and delete by domain ID, with explicit deletion confirmation and dependency checks. Each domain has a DNS page at `/orgs/{slug}/mail/domains/{id}/dns` that displays MX when the server FQDN is set, SPF and DMARC values, and the active DKIM TXT record when configured. The same page supports CSRF-protected SPF and DMARC policy updates. Server Admins can manage mailboxes and review aliases across organizations under `/server/{admin_path}/users` and `/server/{admin_path}/mail/domains/aliases`. Mailbox passwords are hashed with Argon2id and are not included in API responses. Alias sources must use a domain owned by the organization; destinations may be local or external email addresses. Custom panel-domain creation returns a TXT verification value at `_verify.{domain}` and records successful ownership proof. Verified active hostnames are resolved to an owner binding in request context, including one-label wildcard routing. The custom-host root sends User domains to `/users` and Org domains to their owning `/orgs/{slug}` namespace; Org paths for other slugs are rejected. Non-wildcard custom domains can obtain certificates through HTTP-01 or TLS-ALPN-01 when the matching challenge listener is publicly reachable. Wildcards require DNS-01. The custom-domain SSL form accepts any lego provider and a JSON object of provider environment variables; the corresponding API POST accepts `dns_provider` and `dns_credentials`. Credentials and ACME cache data are encrypted at rest, and credentials are never included in responses. Server Admins can review all enrolled custom domains, suspend or restore eligible domains, force-delete enrollments, request certificate renewal, and inspect events for active domains at `/server/{admin_path}/domains/{domain}`. The `/server/{admin_path}/domains/audit` page also retains events for deleted domains. The versioned API uses `/api/{api_version}/users/domains` and `/api/{api_version}/orgs/{slug}/domains` for tenant management, and `/api/{api_version}/server/{admin_path}/domains` for Server Admin listing, inspection, suspension, restoration, deletion, and certificate renewal.

The authenticated Server Admin's own account pages are under `/server/{admin_path}/{admin_username}/`: `profile`, `preferences`, `notifications`, and `profile/security`. Profile changes, optional OpenPGP public-key registration, display preferences, per-event WebUI/email notification preferences, and TOTP enrollment use server-side forms and persist to the users database. Registered admin keys receive encrypted security-report notifications; when no admin key is registered, the configured admin contact receives an AES-256-GCM encrypted attachment. Notification preferences are stored as one JSON document per admin; required security events cannot be disabled. Event email preferences override the server-wide defaults. WebUI notification delivery remains incomplete.

Organization mail operations include `/orgs/{slug}/mail/domains`, `/orgs/{slug}/aliases`, `/orgs/{slug}/mailboxes`, and `/orgs/{slug}/forwards`. Forwarding forms list the organization's rules and support create, update, and confirmed delete operations. Destinations are validated email addresses, up to 20 per rule; mailbox deletion removes its forwarding rules in the same database transaction.

Panel TLS and the configured FQDN's Let's Encrypt settings are managed at `/server/{admin_path}/ssl`. The form supports HTTP-01, TLS-ALPN-01, and DNS-01 using the full lego provider list; DNS credentials are encrypted in configuration and masked in views. The versioned admin API supports GET/PATCH on `/api/{api_version}/server/{admin_path}/ssl` and renewal at `/api/{api_version}/server/{admin_path}/ssl/renew`. ACME cache, account state, and issued certificate material are encrypted in the server database. Changes require a server restart.

Admin usernames cannot match a fixed Server Admin section name such as `settings`, `domains`, or `security`. Existing collisions are renamed with a numeric suffix during schema setup and recorded in the audit log.

## Preferences and public pages

`/server/preferences` provides the supported language preference. Theme preference and essential-cookie acknowledgment are stored in same-site cookies. Static assets are served under `/static/`; the offline page is `/offline.html`.

The JSON response from `/server/healthz` includes the latest discovered public IPv4 and IPv6 addresses and their check time. IPv4 uses an external lookup; IPv6 uses the first active interface address that is globally routable. Discovery runs at startup and every 12 hours.

## Public reporting form

`/server/contact` is an unlinked, noindex reporting form for abuse and terms violations, DMCA notices, and privacy requests. Its chooser links only to those form types. The route does not accept support requests, bug reports, feature requests, or general feedback. `/server/security` is the reporting entry point for deployed-instance vulnerabilities. The contact form applies same-origin checks, a one-use signed form token, a self-hosted challenge, a hidden honeypot, a review-and-confirm step, and in-memory rate and duplicate controls. Reports are sent to the configured role recipient with the sender address as `Reply-To`; report contents are never included in logs. `server.pages.contact.enabled: false` disables the HTML and API form routes.


Security disclosure reports that arrive through `/server/contact?security_id=…` are encrypted with the active project OpenPGP key before database storage, or with the configured AES-256-GCM key when no project key exists. The admin report list and detail pages are session protected; report viewing and updates are audited without report content. Status updates are monotonic, notify the researcher by email when SMTP is available, and can publish opted-in acknowledgments at `/server/security/thanks`. Researchers receive a tracking ID in the response and a one-use-per-day status link by email when SMTP delivery succeeds. The daily `security_cleanup` task removes only closed reports after `server.security.reports.retention_days` (default `365`) and retires old private key files after the 30-day grace period; acknowledgments are retained.

The disclosure admin interface includes the report list, detail, update, keypair, policy-editing, and acknowledgment-management routes. The policy editor saves the Markdown rendered on `/server/security/policy`; the acknowledgment manager controls each entry's visibility, credit label, and display order. The public policy and acknowledgments pages are read-only.
